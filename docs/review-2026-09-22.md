## 0. 一页结论

**内容与契约层是稳的**：全部校验通过，上轮整改的 58 项没有回退，上轮列为“值得保留”的八处设计都还在。
**但有两处 P0**，其中一处是安全缺口、此前没被发现；另有四处 P1 决定了这套技能能不能放心交给真实学生用。

| 维度 | 状态 | 一句话 |
|---|---|---|
| 未成年人心理安全 | 🔴 **P0** | 13 个学生端技能的正文与 references 里没有任何危机处置，危机例外对它们等于不存在（§2.1） |
| 合规定位 | 🔴 **P0**（业务决策） | §2.A 暂缓项原样未动；教育部 2025《中小学生成式人工智能使用指南》又带来四处新缺口，其中“小学生独自使用”与 20 个技能直接冲突（§2.2） |
| 行为质量 | 🟠 P1 | 396 条回归用例**从未运行过**；11 个版本的措辞改动对技能行为的影响没有任何证据（§2.3） |
| 学科内容正确性 | 🟠 P1 | 教研员署名审校仍未做；示例题机器验算只覆盖 4 份文件 11 条断言；2026 秋教材换版（§2.4） |
| 工程门禁 | 🟠 P1 | 仓库**没有 CI**：“门禁”只是本地脚本，推送前没人跑就等于没有（§2.5） |
| 市场遗留 | 🟠 P1 | ClawHub 上还有 442 个旧版本可按版本号安装，含审计查出 26 处“教错”的 v2.0 系列，以及 3 个版本号比 2.1.12 还大的测试版（§2.6） |
| 分发层与版本策略 | 🟡 P2 | `sync-shared.mjs` 长成 510 行的裁剪引擎且无测试；全库锁步版本号让每次改一处就要重发、重扫 58 个（§2.7–2.8） |
| 篇幅与文档 | 🟡 P2 | 半数 SKILL.md 超过 500 行；description 被扫描轮次塞长；changelog 过半是扫描叙事（§2.9–2.11） |
| 密钥与凭据 | ✅ | 工作区与全部 git 历史无密钥；发布凭据在仓库外 |
| 市场现状 | ✅ | ClawHub 与 SkillHub 均 58/58 @ 2.1.12；ClawHub 扫描 40 clean / 18 需复核，已到地板（§3） |

**一句话**：技术整改已经收敛，剩下的要紧事一半是**补安全与验证的最后一公里**（危机全覆盖、跑一次行为回归、建 CI），
一半是**项目方的业务决定**（合规定位、旧版本、版本策略）。新学科扩展应排在这两件之后，否则新技能会原样继承同样的缺口。

## 2. 发现（按严重度）

### 2.1 🔴 P0 · 危机例外没有覆盖全部学生端技能

**证据**：以下 13 个学生端技能的 SKILL.md 与 references 中**一次都没有**出现危机处置或对 `shared/crisis-exception.md` 的引用：

> 语文 `grammar-tracker`、`material-library`、`reading-decoder`；英语 `grammar-coach`、`vocabulary-dna`；
> 数学 `concept-explainer`、`word-problem-coach`；物理 `concept-intuition`、`lab-coach`、`modeling-coach`；
> 通用 `cornell-notes`、`cross-subject-detective`、`im-reminder`

它们的包里其实随附了 `shared/crisis-exception.md` 与 `crisis-referral-protocol.md`（`sync-shared` 发给全部 58 个技能），但**模型只读正文指向的文件**，没人指路，这两份文件就是摆设。以英语词汇DNA 为例：全文没有任何对“我记不住、我太笨、不想背了”这类话的处理，更没有危机出口；IM 提醒是学生最常“顺手回一句”的入口，同样没有。

**根因**：校验规则 S1（`scripts/check-skills.mjs:122,226`）只在正文出现情绪词（焦虑/放弃/挫败/家长看板…）时才强制引用危机协议；回归用例规则 E5 也只要求这一批技能写 crisis 用例。v2.1.0 把它设计成“涉及情绪才需要”，但危机信号不挑场景——学生在背单词时一样可能说出“活着没意思”。

老师端另有 10 个技能没有危机引用。其中命题、备课、实验类技能影响小；`T/independent/homework-tracker`、`student-intake`、`schedule-manager` 会接触老师转述的单个学员情况（未交作业的原因、试听访谈、请假缘由），建议一并补上老师版片段。

**修法**（纯技术，不涉及合规决策）：
1. 13 个学生端技能补一段危机例外（与其余 18 个学生端技能同一写法，放在流程开始前）+ references 列表加一行；老师端三个补老师版片段。
2. S1 改为：`student/` 下全部技能必须引用危机协议，不再以情绪词为条件；E5 同步为每个学生端技能至少一条 crisis 用例。
3. changelog 对 v2.1.11 那句话出勘误。

### 2.2 🔴 P0 · 合规定位：§2.A 仍暂缓，2025 使用指南带来四处新缺口

§2.A 的判断不变：**面向义务教育阶段学科类场景使用前，必须先在业务层面确定定位**，这不是技术整改能关闭的。

新情况是：你在[新学科扩展路线图](roadmap-new-subjects.md) §1.6 里已经对照了教育部基础教育教学指导委员会 2025 年 5 月的《中小学生成式人工智能使用指南（2025 年版）》，并把它标为“随时做”。本次核对，那四条都还没落地，而且第一条比路线图估计的更直接：

| 指南要求 | 本库现状 | 严重度 |
|---|---|---|
| 小学阶段**禁止学生独自使用**开放式内容生成功能 | 20 个学生端技能的 `grade_bands` 含小学学段；`shared/grade-bands.md:38` 对学科教练的规定是：小学中段“部分（需监护人陪同）”，**小学高段“适用（降级版）”、不要求陪同** | 🔴 直接冲突 |
| 教师不得把 AI 作为替代性教学主体、不得直接用 AI 生成内容评价学生 | 26 个老师端技能中 20 个已有“生成待确认条目、老师确认后落库”的机制，方向一致；但没有一处**明文**写出这条边界 | 🟠 缺表述 |
| 严禁把考试试题（启用前统考密卷）输入 AI | 三个命题技能（`T/general/exam-designer`、`T/math/math-exam-designer`、`T/english/english-assessment`）没有任何保密边界；`SECURITY_BASELINE.md` 无此条 | 🟠 缺边界 |
| 学生避免输入个人信息；避免用 AI 参加考试 | `SECURITY_BASELINE.md` 规定的是“不记录”，不是“提醒学生别输入”；学科技能没有“正在进行的考试”识别 | 🟡 缺提示 |

**建议**：这四条里，第二到第四条是纯表述与边界补充，不改变产品定位，可以不等 §2.A 的业务决定先做；**第一条需要你决定**——是把小学学段改为“仅在监护人或老师在场时使用”（改 `grade-bands.md` 一处 + 20 个技能的开场确认），还是把学科类技能的 `grade_bands` 收回到初中及以上。

### 2.3 🟠 P1 · 回归用例从未运行

`evals/` 有 58 份、396 条用例（触发 106 / 不触发 123 / 降级 70 / 授权 62 / 危机 35），`check-evals.mjs` 在门禁里检查它们的**结构与覆盖**。但 `scripts/run-evals.mjs`（把 SKILL.md 喂给模型逐条对话、再由判卷模型对照 `expect` 打分）**从未运行过**——仓库里没有 `evals/report/`，git 历史里也没有任何运行记录。

这件事在 v2.1.1 时影响不大；现在影响变大了：之后 11 个版本在技能内容上累计约 1300 行增、940 行删，很多是在 description 和边界段里加同意门与限定条件。**这些改动有没有让技能变得更难触发、更爱拒绝、更啰嗦，目前没有任何证据**——扫描器只看安全口径，不看教学效果。

**建议**：先全量跑一次（约 800 次模型调用：被测一次 + 判卷一次），报告入库作为基线；此后每次发版只跑改动过的技能。结果非确定，用来发现回归，不做门禁。

### 2.4 🟠 P1 · 学科内容正确性仍缺第二道防线

- **教研员署名审校**仍未开始（上轮 §5 阶段 3 唯一未完成项）。上轮查出的 26 处“教错”是开发侧自查修正的。
- **机器验算覆盖很薄**：20 份含示例题的文件带“示例题验算：日期”声明，但只有 4 份写了可由 CI 求值的 ```verify``` 断言（共 11 条）。其余 16 份的“验算”是自述，门禁只能检查日期没过期，检查不了答案对不对（这正是 16 条 X3 警告）。
- **2026 秋教材换版**（路线图 §1.2）：references 里的知识点位置与例题需要按新教材核对，九年级物理化学还在过渡期。

**建议**：把教研审校与教材换版核对合成一件事做；审校时顺手把关键数值写成 ```verify``` 断言，让下一次换版能由 CI 兜住。

### 2.5 🟠 P1 · 没有 CI

仓库没有 `.github/workflows/`，也没有 git hook。上轮评审和 changelog 里反复说的“CI 门禁”，实际是 `npm run check` 这个**本地脚本**——推送前有人跑、并且看的是退出码，它才起作用。v2.1.9 就出过一次：校验失败了，但因为只看了输出尾部，带着 Z1 错误推了上去，下一次提交才修掉（`5393c72`）。

**建议**：加一个 GitHub Actions 工作流，推送与 PR 时跑 `npm install && npm run check`。注意 `.gitignore` 里忽略了 `package-lock.json`，CI 用 `npm install` 而不是 `npm ci`，或者把锁文件纳入版本管理以固定 ajv 版本。

另一处门禁缺口：`check-skills.mjs` 遍历时跳过了 `tools/`，所以对外发布的 `tools/xiaozhi-skill-creator` 不受内容级校验（F1/F3/H1/Z1 等）。它教别人怎么写技能，更应该守同样的规矩。

### 2.6 🟠 P1 · ClawHub 上旧版本仍可安装

2.1.4–2.1.11 已撤回（460 个版本，可逐个恢复）。但 `latest` 以外仍在线的版本还有 **442** 个：2.1.0–2.1.3 共 228 个、2.0.x 61 个、1.x 150 个，另有语文语法追踪器上 3 个 `99999.0.x` 版本。

默认安装走 `latest`（2.1.12），这部分没问题；风险在于**指定版本号仍能装到旧版**。`99999.0.x` 更要紧：按语义版本它们比 2.1.12 还“新”，任何按最高版本号而不是 `latest` 标签解析的客户端都会装到它们——古文对话当年被迫把版本号映射成 `1000000.N.0`，就是同一类问题。其中 v2.0 系列就是 2026-09-03 审计查出 26 处学科错误与全部合规问题的版本；2.1.0–2.1.3 缺少之后补上的协议硬授权与多处会话边界修正。

**建议**：`latest` 以外全部撤回，至少先撤 `99999.0.x` 与 v2.0 系列（工具已就绪：`scripts/publish/withdraw_clawhub.py`，撤回可逆）。需要你确认，尤其是古文对话那个 slug 上 2.1 之前的历史版本。

### 2.7 🟡 P2 · 分发层成了一台没有测试的裁剪引擎

`scripts/sync-shared.mjs` 从“把共享约定复制进每个包”长成了 510 行的裁剪引擎：按行解析中文否定语境（“不读/不写/❌”、行尾顿号带到下一行、“→ 由 X 维护”）、维护多张别名与路由表、解析老师端 SKILL.md 的“读：/写：”声明块（含跨行括号）、按交接类型配对写回目标、递归裁 `$defs`、区分收发方角色。它的正确性目前只靠两件事保证：输出能被 Ajv 编译、`--check` 重跑结果一致。**两者都查不出“裁多了”或“裁少了”**——v2.1.10 解析器漏认跨行声明头、组卷技能的 `writes` 变成空列表，是靠人眼看输出发现的。

还有一层语义变化值得写进架构文档：裁剪后的副本已经是**按技能收窄的契约**（例如 `subjectExtensionPatch` 只放行正文提到的子分支），平台若拿技能自带的副本做校验，一次 SKILL.md 措辞改动就可能让原本合法的写回被拒。`docs/architecture.md` 对裁剪规则的描述还停在 v2.1.6（只讲了否定语境与顶层裁剪）。

**建议**：给每个技能的 `x-skill-scope`（reads / writes / paths / fields）生成一份快照入库，改动在 PR 里以 diff 出现、由人审；架构文档补上 2.1.9–2.1.12 加的规则与“副本即收窄契约”这一点。更根本的选项见 §2.8。

### 2.8 🟡 P2 · 全库锁步版本号：一处改动 = 58 个重发、重扫

D1 规定全库唯一版本号，任何随包内容变化都要全库升版。好处是一致；代价在这两周变得很具体：

- **每次发版都重发 58 个**：ClawHub 约 100 分钟；SkillHub 按 100 次 / 24 小时固定窗口限流，一次全量占掉 58 次，同一窗口里发第二版必然卡住（09-05、09-06 各卡了约 11 小时）。
- **每次发版都重扫 58 个**：扫描判定每轮有 3–5 个技能在内容不变的情况下翻转。锁步发版意味着**没改的技能也要重新掷一次骰子**——2.1.11 修好的技能在 2.1.12 被等量“翻回去”，40/18 就这样持平。这 11 个版本的“打地鼠”手感，相当一部分来自这里。
- 路线图 §0 已经算到：加新学科后全库约 90 个技能就撑破 SkillHub 单窗口配额。

**这是一个需要你决定的取舍**，两条路：（a）保留锁步版本，但只在真有随包变化时发版、每个窗口只发一次；（b）改为按技能独立版本号，只发内容真变了的技能——代价是 D1 与 schemaVersion 单值枚举要重新设计。附带一个推断：2.1.4 只改了两份共享约定的措辞、给四份 references 加了验算断言，没有改任何技能行为，扫描却从 2.1.3 的 56 clean / 2 掉到 39 / 19——**那次骤降更可能来自扫描器侧口径变化**，而不是内容变差。

### 2.9 🟡 P2 · 篇幅：SKILL.md 与 description 都偏长

- **SKILL.md 正文**：中位 510 行，14 个超过 550 行，最长的学习DNA 837 行。Agent Skills 的渐进披露原则是正文只放“每次都要用”的内容、细节下沉到 references；正文越长，每次激活的上下文成本越高，关键规则也越容易被淹没。
- **description**：中位 296 字，11 个超过 350 字（最长 402）。扫描轮次往 description 里加了大量同意门与限定条件，但 description 的首要用途是**路由**。建议收敛到“做什么 + 什么时候用 + 不做什么（转给谁）”三句，授权细节留在正文。
- 学习DNA 正文里还留着两处给扫描器看的说明（`SKILL.md:131`“对应扫描器 SQP-3”、`:773`“对应扫描器对‘教师写回’的要求”），对模型和读者都没有用，可删。

触发路由本身是健康的：384 条 description 触发句**跨技能零重复**，上轮点名的五组冲突句基本已从 description 中消失。真实的路由质量要等 §2.3 的触发 / 不触发用例跑出来才有数。

### 2.10 🟡 P2 · 文档

- **changelog 被扫描叙事占据**：475 行里 v2.1.2–v2.1.12 这 11 个版本占 267 行，大部分是扫描判定、翻转表与归因。这些分析有价值，但读者是装技能的人，他们关心行为变了什么。建议把扫描分析移到单独文档（如 `docs/archive/clawhub-scan-2026-09.md`），changelog 每个版本只留行为变化与迁移说明。
- **上一份评审的状态头过期**：`review-2026-09.md` 顶部仍写“当前状态：v2.1.1”。本次已加一行指向本文。
- **路线图未入库**：`docs/roadmap-new-subjects.md` 未跟踪，README 里指向它的链接也未提交。两者需要一起提交，否则会出现断链。本次评审没有替你提交。

### 2.11 🟡 P2 · 小项

- `S/english/listening-trainer`：边界写“发音问题一律转英语口语陪练”（`SKILL.md:52`），而“语速太快”一段让学生慢速、常速各跟读一遍（约 `:296-307`）。跟读是正当的听力练法，写明“跟读只为听辨、不评发音”即可消除字面矛盾——这是 2.1.12 扫描里少数站得住的判定之一。
- `S/general/cornell-notes`：归档那一步没有一句“笔记会长期保存、随时可以删”的显著说明（放正文，不放 description，见 §2.9）。
- 两个 Windows 计划任务（`xiaozhi-skillhub-publish`、`xiaozhi-skillhub-verify`）是一次性的，已无下次运行，可以删掉。
